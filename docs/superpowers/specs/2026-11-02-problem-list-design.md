# 문제 목록 홈 화면

작성일: 2026-11-02

## 왜

지금 `/`는 홈이 아니다. 로더에서 곧장 첫 문제로 리다이렉트하고, 문제를 바꾸는
수단은 상단바의 `<select>` 하나뿐이다.

사용자의 말: **"당연히 있어야 할 화면"**이고, **"기능이 확장되고 규모가
커진다면"** 필요하다. 즉 오늘의 불편을 푸는 일이 아니라 나중에 맞는 모양을
미리 갖추는 일이다. 문제는 **최소 수십 개**를 예상하고, 사용자가 **직접 만들
수 있기를** 바란다(만드는 기능 자체는 이번 범위 밖).

다음에 풀 문제를 고를 때 기준은 **난이도**다. 기본 정렬이 난이도순이어야 하고,
정렬을 바꾸는 기능도 있어야 한다.

## 목표

- 수십 개가 쌓여도 훑어서 고를 수 있는 목록
- 내가 무엇을 풀었는지가 보일 것
- 지금의 다크 디자인 시스템·빨간 펜 채점 어휘와 한 제품처럼 읽힐 것

## 비목표

- 문제 직접 만들기(에디터·검증·저장) — 별도 작업
- 완료자 수·정답률 — 서버가 없어 불가능
- 작성 중 코드의 자동 저장 — 아래 "진행 중" 참조. 그 자체로 가치가 있지만
  (새로고침에 작업을 잃지 않는다) 목록과는 별개의 작업이다
- 가상 스크롤·페이지네이션 — 수십 개 규모에서는 불필요. 수백 개가 되면 그때

## 안티골

- 같은 일을 하는 길이 둘이 되는 것. 목록이 생겼는데 상단바 `<select>`도 남으면
  상태 표시와 필터를 두 군데서 관리하게 된다

## 화면

### 레이아웃: 표

사용자가 두 안(표 / 행 카드) 중 **표**를 골랐다. 열이 정렬 가능하고 값끼리
세로로 비교되며, 같은 높이에 더 많이 들어온다.

| 열 | 내용 | 정렬 |
|---|---|---|
| 상태 | 마크 (아래 참조) | — |
| 제목 | `meta.title` | 가능 |
| 난이도 | `Lv.{meta.level}`, 강조색 | **가능 · 기본 오름차순** |
| 태그 | `meta.tags`, 칩 | — |

초안에는 "케이스 수"와 "제한" 열이 있었으나 **뺐다**(사용자 결정). 고를 때
쓰는 정보가 아니고 문제를 열면 바로 보인다. 덕분에 목록이 `meta.json`만으로
완성되어 `repository.list()`를 그대로 쓸 수 있다 — 두 값은 `testcases.json`에
있어서, 넣으려면 작성 포맷에 중복 기록하거나 모든 문제의 테스트 데이터를 홈
화면에서 미리 불러와야 했다.

상단에 진척도 한 줄: `24문제 중 9개 통과` + 얇은 막대.

컨트롤: 제목·태그 검색 입력, 난이도 필터, 상태 필터, 태그 필터.

### 상태 네 가지

마크는 채점 화면의 빨간 펜 어휘를 그대로 쓴다. **진행 중만 예외**다 — 통과와
실패는 채점자가 남긴 결과지만 진행 중은 아직 채점받지 않은 내 쪽의 상태라
결이 다르다. 사용자가 후보 넷 중 **점 세 개**를 골랐다(○·╱가 둘 다
동그라미/선 계열이라 세 번째도 같은 계열이면 작은 크기에서 서로 먹힌다).

| 상태 | 마크 |
|---|---|
| 통과 | `○` 빨간 펜 동그라미 (채점 화면의 pass와 동일) |
| 실패 | `╱` 빨간 펜 사선 (채점 화면의 fail과 동일) |
| 진행 중 | `···` 점 세 개, `--ink-2` |
| 미시도 | 빈칸 |

미시도를 빈칸으로 두는 것은 **내 판단**이다. 푼 문제가 눈에 띄게 하려는 의도.

### 상태는 저장하지 않고 계산한다

새 상태 필드를 따로 두지 않는다. 두 기록에서 유도한다 — 제출 기록과, 이미
있는 작성 중 코드(`draftStore`). 위에서부터 먼저 맞는 것을 쓴다.

1. **통과한 적이 있다** → **통과**
2. 제출한 적 있지만 통과한 적은 없다 → **실패** (부분 통과도 여기)
3. `draftStore`에 코드가 있다 → **진행 중**
4. 그 외 → **미시도**

**진행 중의 정확한 의미**(사용자 결정): `draftStore`는 타이핑할 때가 아니라
`테스트 실행`이나 `제출`을 누를 때만 기록한다(`IdePage.tsx`의 두 호출처).
따라서 3번은 실질적으로 **"공개 테스트를 한 번이라도 돌려봤고 아직 제출하지
않은"** 상태를 뜻한다. 타이핑만 하고 떠나면 흔적이 없어 미시도로 남는데,
풀이를 써놓고 한 번도 돌려보지 않는 경우는 드물어 의도한 "쓰다 만 문제"는
거의 다 잡힌다. 진짜로 타이핑 시점부터 잡으려면 자동 저장이 필요하고, 그건
별개의 작업이다(비목표 참조).

`draftStore.setDraft`는 **코드가 스타터와 같으면 항목을 지운다.** 그래서
스타터 그대로 테스트만 돌린 문제는 미시도로 남는다 — 의도한 동작이다. 이
삭제 규칙이 상태 판정의 근거가 되므로 바꿀 때 주의해야 한다.

공개 테스트만 돌린 것은 통과/실패를 만들지 않는다 — 사용자 확인.

**통과는 한 번 따면 유지된다**(**내 판단**). 나중에 망가진 코드를 제출해도
통과로 남고, 진척도 숫자가 줄어들지 않는다. 연습 기록에서 "풀었던 것"은
실험했다고 해서 사라지지 않아야 한다고 봤다. 그래서 1번 규칙이 최신 제출
기록보다 우선한다.

실패한 뒤 코드를 더 써도 **실패로 남는다**(**내 판단**). 제출 기록이 작성 중
코드보다 강한 신호라고 봤다.

### 그 밖

- 행 전체가 링크. 키보드 위아래 + Enter
- 필터 결과 0건이면 "조건에 맞는 문제가 없습니다 · 필터 초기화"
- 문제가 3개뿐인 지금은 목록이 짧다. **별도 컴포넌트를 만들지 않는다**
  (**내 판단**) — 읽기 좋은 최대 폭으로 가운데 정렬해 3줄이 허공에 뜨지 않게
  하는 정도로 둔다. "다음에 풀 문제" 같은 추천 블록은 만들지 않는다
- **"다음 문제" 버튼을 만들지 않는다**(**내 판단**). 통과 후에는 목록으로
  돌아가는 것이 진척도가 갱신되는 걸 보는 흐름이기도 하다. 만들려면
  `/problems/:id` 로더가 목록을 다시 알아야 해서, 아래 정리와 충돌한다

## 데이터

### 새 저장소: 제출 기록

`draftStore`와 같은 패턴(zustand + `persist`)으로 문제별 제출 기록을 남긴다.

```ts
interface SubmitRecord {
  passed: number;
  total: number;
  at: number;         // 마지막 제출 시각 (epoch ms)
  solvedAt?: number;  // 처음 통과한 시각. 한 번 생기면 지우지 않는다
}
// key: ProblemId
```

- `solvedAt`이 있으면 통과
- 제출이 `passed === total && total > 0`이면 `solvedAt`을 **없을 때만** 채운다

쓰는 시점은 **제출이 끝났을 때 한 번**이다. `useRun`이 `kind === 'submit'`인
실행의 `RunReport`를 받는 자리. 중지됐거나(`cancelled`) 치명적 오류(`fatal`)로
끝난 실행은 기록하지 않는다(**내 판단**) — 채점이 성립하지 않았기 때문이다.

localStorage가 없거나 읽기에 실패해도 앱이 죽지 않아야 한다. `draftStore`가
이미 그렇게 하고 있으니 같은 방식을 따른다. 저장소 이름은 `js-ide:drafts`와
같은 체계를 쓴다. 과거 데이터가 없어 마이그레이션은 필요 없고, 모양이 맞지
않는 값은 무시하고 미시도로 취급한다.

## 라우팅

| 경로 | 지금 | 바뀐 뒤 |
|---|---|---|
| `/` | 첫 문제로 리다이렉트 | **목록** |
| `/problems/:id` | IDE | 그대로 |

필터·검색·정렬은 **URL 쿼리에 담는다**(**내 판단**). 해시 라우터이므로
`#/?q=...&level=1&status=todo&sort=title&dir=desc` 형태. 새로고침과 뒤로가기에서
잃지 않고 링크로 공유도 된다.

`/problems/:id`의 로더는 지금 목록도 함께 불러 `<select>`에 넘긴다.
드롭다운이 사라지므로 그 부분을 정리한다.

### IDE 상단바

`<select>`를 **없애고** "← 목록" 링크로 바꾼다. 수십 개 규모에서 네이티브
select는 찾는 도구로 쓸모가 없고, 그 일은 목록이 훨씬 잘한다. 같은 일을 하는
길이 둘이면 상태와 필터를 두 군데서 관리하게 된다(안티골).

지금 어디 있는지는 보여야 하므로 **현재 문제 제목을 글자로** 남긴다.

**"← 목록"은 보던 목록 상태를 들고 간다**(**내 판단**). 목록에서 문제로 들어갈
때 그 시점의 쿼리 문자열을 라우터 state로 넘기고, 링크가 그것을 되돌린다.
문제 URL로 바로 들어온 사람은 넘겨받은 state가 없으므로 필터 없는 목록으로
간다.

## 모바일

760px 이하에서는 표를 가로로 늘어놓을 수 없다. 각 행을 **쌓인 카드**로 바꾼다
— 첫 줄에 마크 + 제목, 둘째 줄에 난이도 · 태그. 컨트롤은 검색 입력과 필터
버튼만 남기고 접는다(**내 판단**).

기존 작업 영역이 `@media (max-width: 760px)`를 경계로 쓰고 있으므로 같은 값을
쓴다.

## 검증

- 상태 유도 네 갈래를 모두 덮는 유닛 테스트. 특히 **통과 뒤 실패 제출이
  통과로 남는지**, "실패 뒤 수정"이 실패로 남는지, 스타터 그대로 돌린 것이
  미시도로 남는지
- 정렬·검색·필터가 실제로 목록을 바꾸는지 e2e. 필터를 걸어 0건을 만든 뒤 안내
  문구와 초기화가 동작하는지
- URL 쿼리 왕복: 필터를 건 뒤 문제로 들어갔다 "← 목록"으로 돌아오면 그대로인지
- 제출 뒤 목록으로 돌아오면 마크와 진척도가 바뀌어 있는지 e2e
- 좁은 화면에서 가로로 넘치지 않는지 — 기존 레이아웃 테스트와 같은 방식으로
  실제 치수를 잰다
- 단계마다 Playwright 스크린샷으로 **실제 화면을 눈으로 확인한다**

### 기존 테스트에 미치는 영향

`/`가 더 이상 IDE가 아니므로 **기존 e2e 25개 대부분이 깨진다.** 6개 스펙의
`page.goto('/')` 호출부를 문제 경로로 옮겨야 하고, `page.locator('select')`로
문제를 바꾸던 두 곳(`basic.spec.ts`, `layout.spec.ts`)은 다시 써야 한다. CI가
PR마다 `test:e2e`를 돌리므로 선택이 아니라 필수다.

## 빌더가 정한 것

설계 검토에서 빌더가 스스로 정리한 항목들이다. 다시 논의할 필요 없이 그대로
간다.

- 빨간 펜 마크를 `src/ui/`의 공용 프리미티브로 추출한다. 지금 규칙이
  `.case[data-status] .mark::before`로 묶여 있어 CSS Modules에서는 다른 기능이
  재사용할 수 없다. `CaseItem.tsx`와 `theme.spec.ts`의 `li[data-status]` 탐지가
  함께 바뀐다
- 난이도가 같으면 작성자가 지정한 `order`, 그다음 `id` 순
- 진척도 줄은 필터와 무관하게 전체 기준으로 센다
- 목록은 자체 스크롤 영역을 갖는다. 문서 전체가 스크롤되지 않는 기존 불변식을
  지킨다
- `hidden`이 빈 문제를 제출해 전부 통과하면 통과로 친다. 스키마가 허용하므로
  직접 만든 문제에서 나올 수 있다

## 빌더에게 남기는 것

- 표 헤더의 정렬 UI 형태(화살표 토글 / 드롭다운)
- 필터 컨트롤의 구체적 형태 — 기존 `ProblemPicker`가 커스텀 화살표를 붙인
  네이티브 select를 쓰므로 거기 맞추는 편이 일관적이다
- 진척도 막대의 치수와 비율 표현 방식. 색은 `--ok`
- 태그 필터가 다중 선택인지 단일인지
